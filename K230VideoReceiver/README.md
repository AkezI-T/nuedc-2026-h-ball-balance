# K230 JPEG 实时视频接收器

当前工作分支为 `v1-speed`：识别、显示和图传恢复到标签 `v1` 的实现，仅扩展 K230 内部钢球速度估算以及五字段 `@VIS` 协议。V2 已独立保存在分支和标签 `v2`。

当前版本同时保留两种自定义 JPEG 图传：

- `JPEG + UDP`：模型版和传统识别版均为320x240、质量40、目标15 FPS，优先低延迟，允许丢帧；
- `JPEG + TCP`：640x480、质量70、目标15 FPS，优先完整可靠。

链路为：

`K230摄像头 -> 硬件JPEG编码 -> UDP/TCP -> 手机热点 -> Windows电脑显示`

旧RTSP脚本保留为技术对照，不再作为默认方案。当前正式上位机已经支持实时画面、链路状态和MP4录像；传统CV脚本与车载ESP32-S3通过UART1控制，模型脚本暂时保留旧UDP `9020`控制实现。

## 图传协议

### TCP 帧协议

每帧由16字节帧头和一幅完整JPEG图像组成，所有整数采用网络字节序：

| 字段 | 大小 | 说明 |
|---|---:|---|
| `KJPG` | 4字节 | 固定帧标识 |
| `sequence` | 4字节 | 帧序号 |
| `width` | 2字节 | 图像宽度 |
| `height` | 2字节 | 图像高度 |
| `jpeg_size` | 4字节 | 后续JPEG数据长度 |

TCP 默认端口为 `9000`。

### UDP 分片协议

UDP 默认端口为 `9001`。电脑先向 K230 发送 `KHEL` 心跳，然后 K230 将每个 JPEG 拆成不超过 1200 字节的数据报。20 字节分片头结构如下：

| 字段 | 大小 | 说明 |
|---|---:|---|
| `KUJP` | 4字节 | 固定分片标识 |
| `sequence` | 4字节 | JPEG 帧序号 |
| `fragment_index` | 2字节 | 当前分片序号 |
| `fragment_count` | 2字节 | 本帧总分片数 |
| `width` | 2字节 | 图像宽度 |
| `height` | 2字节 | 图像高度 |
| `jpeg_size` | 4字节 | 完整 JPEG 长度 |

每包最多携带 1180 字节 JPEG 数据。缺少任何分片时，电脑端直接丢弃该帧。

## 1. K230 启动图传

### 纯图传模式

1. 在 CanMV IDE 中打开 `k230_tcp_jpeg_sender.py`。
2. 停止其他正在占用摄像头的脚本。
3. 运行发送端，等待串口显示：

```text
[tcp] listening on 10.43.133.238:9000
[jpeg] frame=640x480 sensor=30fps send=15fps quality=70
```

### 钢珠识别 + 本地显示 + UDP 图传模式

1. 确认模型目录位于 `/sdcard/st/mp_deployment_source/` 或 `/sdcard/mp_deployment_source/`。
2. 在 CanMV IDE 中打开并运行 `k230_tcp_jpeg_detect.py`。该脚本当前默认 `STREAM_TRANSPORT = "udp"`。
3. K230 屏幕显示 `y=55~135` 红色 ROI、带实心中心点的绿色钢珠框、中心黄色全画幅十字准星，以及正负 `10 cm` 的竖向刻度线。当前先按屏幕每格 `0.2 cm` 等差标定，像素偏移表为 `(27, 53, 80, 107, 133, 160, 187, 213, 240, 267) px`。紫色竖线表示 ESP32-S3 指定的目标位置，左下角第一行显示 `TARGET +50MM` 形式的当前目标，第二行显示 `E_PX` 与速度 `V`，速度单位为640坐标系像素/秒。屏幕同时显示 `BALL`、`WIFI`、`UDP` 和帧率状态；控制链路未握手时显示 `CTL WAIT 9020`，收到车载 ESP32 的 HELLO 后绿色显示 `CTL OK <ESP32_IP>`。
4. 电脑端双击 `start_upper_computer.bat`。电脑会发送 `KHEL` 心跳，K230 自动登记电脑地址，无需写死电脑 IP。

集成脚本的摄像头通道分工如下：

| 通道 | 格式与分辨率 | 用途 |
|---|---|---|
| CH0 | 640x480 YUV420SP | K230 标准 480P 硬件显示 |
| CH1 | 320x240 YUV420SP | 质量40的 JPEG 硬件编码和 UDP 图传 |
| CH2 | 320x240 RGB888P | KPU 钢珠识别 |

K230 本地显示恢复为固件标准的 `640x480`，视频层偏移为 `(0,0)`。UDP 图传和模型推理仍保持 `320x240`，因此不会增加无线带宽或 KPU 输入开销。主循环不额外抓取 CH0，避免与 CH2 模型取帧争抢缓冲；管道移动后，ROI 在本地屏幕上更新为 `y=55~135`。

电脑端当前显示 CH1 原始画面，不包含 K230 的 OSD 叠加层。这样可以避免为了画框而在 CPU 中重新编码 JPEG，并保持图传帧率。

### 传统视觉识别 + 320x240 UDP 图传模式

在 CanMV IDE 中运行 `k230_classical_ball_test.py`。该脚本不加载 kmodel，使用固定 `y=55~135` ROI，依次执行灰度阈值、形态学、连通域筛选和 Alpha-Beta 横向跟踪。

摄像头通道分工如下：

| 通道 | 格式与分辨率 | 用途 |
|---|---|---|
| CH0 | 640x480 YUV420SP | 硬件绑定 K230 LCD 彩色视频层 |
| CH1 | 320x240 YUV420SP | 质量40、15 FPS 的 JPEG 硬件编码与 UDP 图传 |
| CH2 | 640x480 GRAYSCALE | 固定 ROI 传统识别与 Alpha-Beta 跟踪 |

CH0 通过 `Display.bind_layer()` 由视频硬件直接送入 LCD，Python 不再抓取、绘制或调用 `Display.show_image(frame)` 提交整幅彩色帧。传统识别版与稳定的模型版统一使用 `30 FPS` Sensor 模式；准线、刻度、识别框和状态文字绘制在独立 ARGB8888 OSD 层，每6个识别帧刷新一次。视频仍使用现有 `KHEL/KUJP` 协议和 UDP `9001`，上位机无需修改即可从帧头读取 `320x240` 分辨率。电脑端收到 CH1 原始彩色画面，不包含 K230 本地 OSD。

本地屏幕绘制中心红色纵横准线、左右各10条灰色等差竖线、红色 ROI、识别候选和球心；收到 `@TGT` 后再绘制紫色目标竖线。ROI 内的蓝色横线位于 `y=95`，表示管道宽度中心；候选评分优先选择纵向范围穿过或接近该线的亮斑，输出球心 `Y` 投影到蓝线，控制只使用候选框宽度中心的横坐标 `X`。等差刻度沿用 `(27, 53, 80, 107, 133, 160, 187, 213, 240, 267) px` 标定。

传统识别脚本使用UART1发送五字段 `@VIS,VALID,E_PX,LAST_E_PX,V_PX_S`，并接收 `@TGT,TARGET_MM`。图传接收端或ESP32控制端未连接时，检测与本地显示继续运行。模型版脚本仍保留旧UDP控制实现，本节UART接线仅适用于传统CV脚本。

为防止画面剧烈扰动导致Python对象暴增或JPEG取流长期占用主循环，传统CV程序设置了硬预算：单帧原始blob超过64个时直接输出无效检测，正常帧最多保留16个高分候选；VENC每轮最多取2帧且使用`timeout=0`；单幅JPEG最多发送128个分片。周期GC会先释放当前图像和候选引用再执行。控制台的`blob/cand/overload`分别表示原始blob数、保留候选数和累计过载帧数。

Wi-Fi连接采用非阻塞重试：脚本启动后立即发起第一次连接，未连接时每隔`30 s`再调用一次连接；离线期间视觉UART继续工作，编码器队列也会持续取空。获得DHCP地址后只创建UDP `9001` JPEG图传，Wi-Fi掉线不会中断`@VIS/@TGT`。

### K230与车载ESP32-S3视觉控制UART

#### 网络层与端口

| 数据 | 传输 | 端口 | 说明 |
|---|---|---:|---|
| JPEG 图传 | UDP | `9001` | 模型版和传统识别版均发送320x240 JPEG分片 |
| 视觉控制 | UART1 | `115200-8N1` | K230与车载ESP32-S3交换VIS、TGT |

视觉控制与UDP `9001` JPEG图传完全独立。控制帧使用ASCII文本并以`\r\n`结束，不包含序号或CRC。

#### 接线

| K230 | ESP32-S3 | 方向 |
|---:|---:|---|
| IO9/UART1_TX | GPIO46/UART1_RX | `@VIS` |
| IO10/UART1_RX | GPIO13/UART1_TX | `@TGT` |
| GND | GND | 共地 |

双方均使用3.3V TTL。K230串口接收采用非阻塞CRLF组帧，ESP32每次目标变化立即发送`@TGT`，并每秒重发当前目标，因此任一侧单独重启后都能自动恢复。

#### K230 到 ESP32-S3：视觉帧

K230传统CV程序每次识别后发送一帧，字段之间使用英文半角逗号，不允许插入空格：

```text
@VIS,VALID,E_PX,LAST_E_PX,V_PX_S\r\n
```

| 字段 | 格式与范围 | 说明 |
|---|---|---|
| `@VIS` | 固定 ASCII 文本 | 视觉帧头 |
| `VALID` | `0` 或 `1` | `1` 表示当前帧检测到钢球，`0` 表示未检测到 |
| `E_PX` | 十进制有符号整数，`-639~639` | 当前钢球中心像素 X 减目标位置像素 X，右正左负；无效帧固定为 `0` |
| `LAST_E_PX` | 十进制有符号整数，`-639~639` | 最后一次出现的钢球位置相对当前目标的像素差 |
| `V_PX_S` | 十进制有符号整数，`-5000~5000` | K230 根据相邻有效检测估算的钢球横向速度，单位为640坐标系像素/秒，右正左负 |
| `\r\n` | 字节 `0x0D 0x0A` | 帧结束符 |

当前协议不包含序号和 CRC，最长一帧为24字节。ESP32-S3 按 `\r\n` 分帧，并检查帧头、字段数量和数值范围。车载ESP32必须按五个数据字段解析，旧版四字段解析器不能直接使用。

有效检测示例：

```text
@VIS,1,-42,-42,350\r\n
```

下一帧未检测到钢球时：

```text
@VIS,0,0,-42,350\r\n
```

启动后尚未出现过钢球时：

```text
@VIS,0,0,0,0\r\n
```

速度由K230内部的 Alpha-Beta 状态估计器计算，参数为 `alpha=0.70`、`beta=0.20`，每次使用真实毫秒帧间隔完成位置预测、测量校正和速度更新。单帧创新量限制为 `120 px`，避免偶发误框把速度直接拉满；连续3帧位置变化不超过2像素时锁定为静止，速度绝对值小于 `45 px/s` 时输出0。短时丢检保留估计速度，距离最后一次有效检测超过 `200 ms` 后固定发送 `0`；速度绝对值限幅为 `5000 px/s`。当 `VALID=0` 时，ESP32只能把速度用于短时状态预测，不应把它当作当前有效测量。

K230完成UART初始化后持续发送`@VIS`，不再等待HELLO或Wi-Fi配对。

#### ESP32-S3 到 K230：目标位置帧

ESP32-S3 使用毫米整数指定钢球目标位置，0 表示摆杆中心点 O：

```text
@TGT,TARGET_MM\r\n
```

| 字段 | 格式与范围 | 说明 |
|---|---|---|
| `@TGT` | 固定 ASCII 文本 | 目标位置帧头 |
| `TARGET_MM` | 十进制有符号整数，`-110~110` | 相对中心点 O 的目标位置，右侧为正，左侧为负，1 mm 对应题目刻度 0.1 cm |
| `\r\n` | 字节 `0x0D 0x0A` | 帧结束符 |

题目任务对应命令：

```text
@TGT,0\r\n       # 稳定在中心点 O
@TGT,50\r\n      # 运行到 +5 cm
@TGT,-50\r\n     # 运行到 -5 cm
@TGT,37\r\n      # 任意指定位置 +3.7 cm
```

车载ESP32在目标位置发生变化时立即通过UART发送`@TGT`，目标未变化时每`1 s`重发一次，以便K230或ESP32单独重启后自动恢复目标。K230收到合法命令后保持该目标，直到收到下一条目标帧。主循环采用非阻塞方式接收，格式错误或超范围命令会被忽略并保留原目标。

机构实测可达范围为 `-110~+110 mm`，其中正负 11 cm 是机械限位点，正负 12 cm 不可达且协议不接受。当前广角像素标定完成到 `-100~+100 mm`，所以固件暂时拒绝绝对值大于 100 mm 的目标；补齐 11 cm 的像素偏移后才能开放限位点。

当前先按屏幕每格 `0.2 cm（2 mm）` 等差标定；像素值按屏幕 `3 mm≈40 px` 对累计位置取整：

| 实际位置 | 屏幕测量 | 像素偏移 |
|---:|---:|---:|
| 0 cm | 0 mm | 0 px |
| 1 cm | 2 mm | 27 px |
| 2 cm | 4 mm | 53 px |
| 3 cm | 6 mm | 80 px |
| 4 cm | 8 mm | 107 px |
| 5 cm | 10 mm | 133 px |
| 6 cm | 12 mm | 160 px |
| 7 cm | 14 mm | 187 px |
| 8 cm | 16 mm | 213 px |
| 9 cm | 18 mm | 240 px |
| 10 cm | 20 mm | 267 px |
| 11 cm（限位） | 待标定 | 待标定 |

目标毫米位置通过相邻厘米标定点进行线性插值，控制误差为：

```text
E_PX = BALL_X - TARGET_X
```

#### 车载闭环与上位机边界

原始 `@VIS` 的唯一接收端是车载 ESP32，不会逐帧上传到上位机。钢球误差直接在车载端形成控制闭环；车载 ESP32 将本机 `@CTRL` 和 TMX UART收到的 `@CAR/@TASK/@MODE` 等协议行通过 Wi-Fi 广播给上位机：

```text
K230 --UART1 @VIS-----> 车载 ESP32 --本地控制--> 电机
K230 <--UART1 @TGT----- 车载 ESP32
K230 --UDP 9001 JPEG-----------------------> 上位机
车载 ESP32 --UDP 9011 控制日志-------------> 上位机
```

车载ESP32根据`VALID`、`E_PX`、`LAST_E_PX`和`V_PX_S`计算电机控制量，并根据当前任务通过UART发送`@TGT,TARGET_MM`。电脑侧不参与控制闭环；UDP `9011`只传输控制日志。

上位机不解析原始 `@VIS`，只监听 UDP `9011` 的控制日志。当前 PySide6 GUI 仍使用界面或启动参数中的 K230 IP接收视频；日志广播不用于识别K230。

## 2. Windows 图传上位机

### 正式 GUI 与录像

确保电脑连接同一个手机热点，然后双击：

```text
start_upper_computer.bat
```

上位机采用 PySide6，启动后固定绑定电脑本地UDP `9001`，并向默认地址 `10.43.133.238:9001` 发送心跳等待画面。主窗口集中显示实时视频、视频链路指标和录像控制；右侧“打开电机监控”按钮会打开独立日志窗口，不再占用主视频区域。

电机监控窗口自动监听 UDP `9011`，不再提供串口选择。窗口固定分成三等列：底盘巡线 `@CAR`、滚球控制与TEST采样 `@CTRL/@TEST`、任务事件 `@TASK/@MODE`及其他`@`协议行。三列分别计数并自动滚动到最新一行。“清理”会同时清空三列和当前保存缓冲，清理前已接收但尚未显示的日志不会重新出现；点击“保存”不再弹出命名窗口，而是在 `Logs` 目录自动生成同一时间戳开头的三份文件：

```text
20260731_161500_123_T4_CAR.log
20260731_161500_123_T4_CTRL.log
20260731_161500_123_T4_EVENT.log
```

文件名中的 `T1` 至 `T6` 表示当前日志对应的任务，TEST模式使用 `TEST`；上位机根据最近收到的任务事件或TEST采样自动填写，当前缓冲中没有任务上下文时使用 `TX`。三份文件分别保存当前未清理的底盘、滚球控制和任务/其他事件日志；某一类当前没有内容时仍会生成对应的空文件，确保每次保存得到完整的一组三文件。

车载 ESP32 在 Wi-Fi 已连接且 UDP 日志 socket 就绪后，会主动广播一次链路成功提示；上位机不合成该日志，收到后原样放入事件列：

```text
@LINK type=UDP_LOG state=CONNECTED device=ESP32S3 port=9011
```

上位机会解析 Wi-Fi日志中的 G3507 任务事件：

```text
@TASK ... type=TASK_BEGIN ...  -> 自动开始录像
@TASK ... type=TASK_END ...    -> 自动停止并保存录像
```

T4/T5/T6还会用运行态 `@TARGET state=TRACK/FROZEN` 或首个
`@CTRL stage=TRACK` 兜底开始录像，避免UDP突发时恰好丢失全部
`TASK_BEGIN`副本；停止和保存仍只认 `TASK_END`。

若开始事件到达时视频尚未出现，上位机会等待第一帧后自动开始录像。K230 视频使用 UDP `9001`，车载ESP32日志使用 UDP `9011`，二者互不占用端口。

录像文件使用固定输出帧率，但按 `TASK_BEGIN` 到 `TASK_END` 的电脑墙钟时间重采样。接收帧率低于输出帧率、UDP丢帧或PREP刷新接收器时，上位机会重复最后一帧保留真实时间轴，不再把十九秒任务压缩成数秒回放。只要任务开始前已经显示过一帧，即使开始事件恰好落在接收器重启期间，也会立即启动录像计时；从未收到过画面时才等待首帧。

当视频流已经识别成功后，上位机收到任务准备事件：

```text
@MODE ... type=ENTER mode=PREP task=T1 ...
```

会异步停止并重新启动一次 UDP 视频接收器，用于刷新接收状态。只要本次运行曾经成功收到过视频，即使PREP到达时画面已经进入“暂时中断”，也会执行刷新。同一准备事件重复发送时按 `eventSeq/type/mode/task/t` 去重，不会连续重启；重启前后均使用固定的电脑本地UDP `9001`，因此K230会把新心跳识别为同一接收端，而不是等待旧随机端口超时。该刷新不改变 `TASK_BEGIN/TASK_END` 的自动录像规则。

录像保存到程序同目录的 `Save` 文件夹。任务自动录像使用任务号作为文件名前缀，停止录制时按结束时间命名，例如：

```text
Save\T3_20260730_143025.mp4
```

T1至T6分别使用 `T1_`至`T6_`前缀；界面手动开始的录像不附加任务前缀。

如 K230 的 IP 发生变化，可以先在界面中修改，也可以启动时指定：

```powershell
.\start_upper_computer.bat --host 新的IP --port 9001
```

同一台电脑上不要同时运行 GUI 和命令行 UDP 接收器，否则 K230 只会向先登记的接收端发送画面。

第一次运行时，如果 Windows 防火墙询问是否允许 Python 通信，需要允许当前网络。

### UDP 命令行调试模式

需要排查链路而不录像时，可以双击：

```text
start_udp_receiver.bat
```

也可以明确指定 K230 地址：

```powershell
.\start_udp_receiver.bat --host 10.43.133.238
```

第一次运行时，如果 Windows 防火墙询问是否允许 Python 通信，需要允许当前网络。

### TCP 回退模式

确保电脑连接同一个手机热点，然后双击：

```text
start_receiver.bat
```

显示窗口中按 `Q`、`Esc` 或关闭窗口即可退出。断线后接收器每隔1秒自动重连。

如果K230的IP发生变化，可在本目录执行：

```powershell
.\start_receiver.bat --host 新的IP --port 9000
```

也可以明确使用项目虚拟环境执行：

```powershell
.\.venv\Scripts\python.exe pc_receiver.py --host 10.43.133.238 --port 9000
```

## 说明

- TCP确保每个JPEG帧完整到达，不再存在H.264 SPS/PPS或宏块损坏问题。
- UDP 不重传、不等待缺失分片；网络波动时表现为丢帧，而不是延迟持续累积。
- **电脑上同时只能运行一个接收程序**。GUI 和命令行接收器不能同时运行。K230 绑定第一个心跳来源后，会忽略其它来源的心跳（日志打印 `忽略额外心跳来源`）；旧版本会把同一帧的分片轮流发往多个接收端，导致任何一端都组不出完整画面。
- K230 端持续取不到编码帧时，串口会周期打印 `GetStream 错误码` 和 `本周期无编码帧`，用于区分编码链路故障与网络故障。
- IDE 中断（软重启）后若出现 `MediaManager, vb config failed(18)`，按板子上的硬件 RESET 键复位再运行，软重启无法彻底清理媒体层状态。
- FireWater和JustFloat用于传输遥测浮点数据，不用于承载视频帧。
- UDP 集成模式在主循环中顺序执行 JPEG 取流、非阻塞发送和 KPU 推理，避免 Sensor 与 VENC 媒体接口跨线程冲突；TCP 回退模式仍使用发送线程。
- 如果集成模式出现资源或模型兼容问题，可立即改回 `k230_tcp_jpeg_sender.py` 验证纯图传链路。
- GUI 录像在电脑端使用 `mp4v` 编码为 MP4，不增加 K230 端负担。
